## Class A — the GUP changed after the Review pinned it

Four bundles fail only `review-pinned GUP YAML still matches on disk`.

    magic-user-spells-1-4-r05  declared d1fd495f…  actual 3652a6ed…
    magic-user-spells-5-9-r05  declared f51568e6…  actual 02155a08…
    playing-the-game-r05       declared 612a57f8…  actual a84bb11c…
    planes-of-existence-r04    declared 917898d0…  actual 27031ada…

**These four bundles are otherwise sound.** Their operation indexes are exactly
well-formed — `csv_row` runs 1..N with the count equalling the row count in every
case, 233, 210, 72 and 22 respectively. Every other precondition passes,
including each bundle's own component checksums.

The defect is provenance, not content. The GUP file on disk is no longer the file
the Review approved, so what the Review certified can no longer be established.
Invariant 21 makes provenance retention a property of the manifest, and I cannot
confirm these rows were the reviewed rows. Integrating them would take the
approval on trust and enter unverifiable lineage into canonical state.

I have deliberately **not** inspected whether the edits were cosmetic. Deciding
that an unpinned change is harmless is source interpretation, which is prohibited
to this role, and the checksum exists precisely so that judgement is not mine.

## Class B — the operation index describes rows that do not exist

Three bundles fail `operation index classifies every CSV row exactly once` with
`KeyError: 'csv_row'`. In each, **no** index entry carries `csv_row`, and the
index declares far more operations than the CSV holds rows:

- `illusionist-spells-r04` — 14 rows, 126 declared (14 additions + 112 pending)
- `psionics-r03` — 14 rows, 217 declared (14 additions + 203 pending)
- `alignment-graph-r02` — 0 rows, 4 declared

The `KeyError` is a symptom. A well-formed entry addresses a row in its own CSV
by `csv_row: N`; these entries carry only `ref`, `source_id`, `edge_type` and
`target_id`, because there is no row to address. The index was written from the
GUP's intent rather than from its rows.

Each bundle declares `rows` equal to what its CSV actually contains, so the
"declared row count matches the CSV" check passes. That check cannot catch this
class: it compares the manifest against the CSV, while the discrepancy is between
the *index* and the CSV.

`alignment-graph-r02` was already rejected on 2026-08-12 and its replacement,
`alignment-graph-r03`, is correct and landed in `INT-20260812-001`. **r02 remains
in the ready queue** because its `supersedes` is null and nothing marks it
consumed, so it will keep re-entering the queue and failing until it is
superseded or withdrawn.

## Remediation

**Builder** — for the three Class B packets, re-issue with the edge rows the index
already describes: 126 rows for illusionist, 217 for psionics. Resolve authored
polarity on every row; `unset` or `heuristic` trips invariant 16 as an introduced
finding and the batch will be rejected again.

**Reviewer** — rebuild `operation_index` from the CSV on the re-issued bundles so
each entry carries `csv_row` and every row is classified exactly once. Note that
an assertion depending on a node the same batch registers belongs under
`pending_additions`, not `additions`. This was the correction that made
`alignment-graph-r03` pass.

**For Class A** — either re-pin the four Reviews against the GUPs as they now
stand, or restore the GUPs to their approved bytes. Whichever is correct is a
question about what was reviewed, and it belongs to the Reviewer, not to me.

**Queue hygiene** — mark `alignment-graph-r02-r01` superseded by `-r03-r01` so it
stops presenting as ready work.
