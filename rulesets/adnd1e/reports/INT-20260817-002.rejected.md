## One defect, three bundles: the bundle ships a third of the rows it indexes

Each of these packets was authored as three separate CSVs in the GUP directory:

| GUP | `edges.csv` | `pending.csv` | `blocked.csv` | total |
|---|---|---|---|---|
| `magic-user-spells-1-4-r08` | 98 | 133 | 2 | 233 |
| `magic-user-spells-5-9-r07` | 48 | 155 | 7 | 210 |
| `psionics-r06` | 14 | 194 | 9 | 217 |

The arithmetic identifies the defect exactly. In every case:

- `operation_index.additions` equals the `edges.csv` row count;
- `operation_index.pending_additions` equals the `pending.csv` row count;
- the manifest's declared `components[0].rows` equals `edges + pending`;
- the highest `csv_row` in the index equals that same total; and
- the Review's approved-row count equals `edges + pending + blocked`.

But the Approved bundle declares **one** edge component, and the file it names
and checksums contains only the `edges.csv` portion. Every component checksum
matches, so nothing was truncated after packaging: the bundle was published this
way. The operation index therefore numbers rows across the concatenation of two
files while the bundle carries one, and `csv_row` 15 through 208 — 99 through
231, 49 through 203 — address rows that are not in the bundle at all.

This is why the failure reads as three separate preconditions. "Declared row
count matches the CSV", "review approved-row count matches the CSV" and
"operation index classifies every CSV row exactly once" are all the same fact
seen from three directions.

## What is *not* wrong here

The upstream work is sound, and the split is a reasonable response to the
dependency rejections in `INT-20260814-003` and `INT-20260815-002`. Separating
rows that apply now from rows pending this batch's own registrations, and both
from rows blocked on the unpublished druid-spells packet, is exactly the right
decomposition of the problem. The row counts reconcile perfectly in all three
packets, which is not what a careless bundle looks like.

The `blocked.csv` rows are correctly excluded: those are the ones depending on
`spell_charm_person_or_mammal`, `spell_heat_metal` and `spell_pyrotechnics`,
which only `GUP-PKT-PHB-054-064-druid-spells-r01` registers and which remains the
one blocked item in the Builder queue.

## Remediation — Reviewer

The approved edge CSV must contain every row its manifest declares and its index
classifies. Emit it as the concatenation of the GUP's `edges.csv` and
`pending.csv`, in the row order the `csv_row` values already assume, so the
component holds 231, 203 and 208 rows respectively. Then re-pin
`components[0].checksum`.

Nothing else needs to change. The operation index, the additions/pending split,
the node registrations and the exclusion of the blocked rows are all correct as
written; they simply describe a file the bundle does not currently carry.

Two alternatives were considered and are **not** what this report asks for:

- Declaring the extra CSVs as additional bundle components. No contract, schema
  or Decision defines a `pending` or `blocked` component kind, and the manifest
  does not declare them, so this would be a new bundle shape and an Architect
  question rather than a packaging fix.
- Reducing the declared row count to the shipped 14/98/48. That would contradict
  the operation index, the Review's approved-row count, and the packet's own
  intent, and it would silently drop rows the Review approved.

The Integrator will not concatenate the files itself: choosing which rows
constitute the approved set is the packaging decision the Review exists to make.
